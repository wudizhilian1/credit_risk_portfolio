# Day 39 实践报告：工程化 v1——告警方案设计与实现（阈值配置 + 通知脚本）

## 1. 练习目标

- 将前期的数据质量监控从“被动检查”升级为“主动告警”，提升数据平台的自动化运维能力。
- 设计告警规则配置表，支持阈值动态调整，避免硬编码。
- 编写 Python 脚本，定期扫描监控表，根据规则发送告警（控制台日志输出，预留邮件/钉钉接口）。
- 建立告警记录表，追踪告警历史和处理状态。

## 4. 遇到的问题与解决方案

| 问题                                                         | 解决方案                                                     |
| :----------------------------------------------------------- | :----------------------------------------------------------- |
| 创建 `dq_alert_history` 表时 `AUTOINCREMENT` 语法错误        | 改用 DuckDB 支持的 `GENERATED BY DEFAULT AS IDENTITY`        |
| `fetch_monitor_data` 中访问 `rule['null_field']` 导致 `KeyError` | 在规则表中增加 `field_name` 字段，并在代码中通过 `.get()` 安全获取 |
| 插入历史记录时 `NOT NULL constraint failed: alert_id`        | 重建表使用正确的自增语法，插入时省略 `alert_id` 列（DuckDB 会自动生成） |
| dq_alert_history的alert_id不能是主键自增                     | 通过get_next_alert_id获取最大的id + 1                        |

## 5. 口径与边界说明

| 要素     | 说明                                                         |
| :------- | :----------------------------------------------------------- |
| 规则配置 | 阈值存储在表中，支持动态修改，无需重启脚本。                 |
| 告警去重 | 当前未实现去重，可后续增加时间窗口限制（如同一规则 1 小时内不重复告警）。 |
| 历史记录 | 保留所有告警，便于事后分析和复盘。                           |
| 通知方式 | 目前使用控制台输出，预留邮件/钉钉接口。                      |

## 6. 性能点

- 告警脚本仅查询最近一次监控记录，数据量小，执行快。
- 可放在每日调度末尾，不影响主流程。

## 11. 思考题

- 如果同一规则连续多天触发告警，如何避免重复通知？（可设置冷却时间，例如告警后 24 小时内不再重复发送。）
- 告警规则中的阈值如何科学确定？（可基于历史数据分布，使用百分位数或标准差动态计算。）
- 如何将告警与工单系统结合，实现闭环处理？（在告警历史表中增加 `is_resolved` 字段，由人工或自动修复后更新。）
