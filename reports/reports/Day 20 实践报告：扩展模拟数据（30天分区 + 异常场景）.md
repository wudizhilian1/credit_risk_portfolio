## 3. 核心任务执行

### 3.1 修改数据生成脚本
将 `generate_demo_data.py` 中的日期范围从 `2024-01-01` 至 `2024-01-10` 扩展为 `2024-01-01` 至 `2024-01-30`，并引入以下异常场景：

| 日期       | 异常类型     | 描述                   | 实现方式                                    |
| ---------- | ------------ | ---------------------- | ------------------------------------------- |
| 2024-01-15 | 申请量突增   | 申请量为平时的2倍      | `day_apply_cnt = NUM_APPLY_PER_DAY * 2`     |
| 2024-01-18 | 渠道数据缺失 | API 渠道无申请         | 生成申请时跳过 API 渠道                     |
| 2024-01-20 | 通过率下降   | 通过率由60%降至30%     | 决策权重调整为 `PASS:REJECT:REVIEW = 3:5:2` |
| 2024-01-25 | 金额异常     | 出现负数金额和超大金额 | 部分记录 `amount` 设为负数                  |

### 4.4 每日通过率监控（突出异常日）

```sql
WITH decision_stats AS (
    SELECT 
        d.dt,
        COUNT(*) AS total_decisions,
        SUM(CASE WHEN d.decision = 'PASS' THEN 1 ELSE 0 END) AS pass_cnt,
        SUM(CASE WHEN d.decision = 'REJECT' THEN 1 ELSE 0 END) AS reject_cnt
    FROM v_decision d
    WHERE d.dt BETWEEN '2024-01-01' AND '2024-01-30'
    GROUP BY d.dt
)
SELECT dt, total_decisions, pass_cnt, reject_cnt,
       ROUND(100.0 * pass_cnt / total_decisions, 2) AS pass_rate,
       ROUND(100.0 * reject_cnt / total_decisions, 2) AS reject_rate
FROM decision_stats
ORDER BY dt;
```

```
+---------------------+-------------------+------------+--------------+-------------+---------------+
| dt                  |   total_decisions |   pass_cnt |   reject_cnt |   pass_rate |   reject_rate |
|---------------------+-------------------+------------+--------------+-------------+---------------|
| 2024-01-01 00:00:00 |              5000 |       1679 |         1687 |       33.58 |         33.74 |
| 2024-01-02 00:00:00 |              5000 |       1686 |         1602 |       33.72 |         32.04 |
| 2024-01-03 00:00:00 |              5000 |       1695 |         1666 |       33.9  |         33.32 |
```

## 6. 口径与边界说明

| 验证项   | 口径说明                                                   |
| :------- | :--------------------------------------------------------- |
| 申请量   | 基于 `v_apply` 按 `dt` 分组计数，`apply_id` 已去重。       |
| 异常金额 | 金额为负数的记录数，用于检测数据质量。                     |
| 通过率   | `PASS` 决策数 / 总决策数 * 100，分母为当日决策总数。       |
| 渠道缺失 | 某渠道在某日无任何申请记录，可能表示数据源问题或渠道下架。 |

## 7. 性能点

- 分区裁剪：查询中指定 `dt BETWEEN ...` 确保只扫描相关分区，验证时可通过 `EXPLAIN` 观察。
- 聚合效率：`GROUP BY dt` 利用分区特性，DuckDB 可并行处理各分区文件。
- 数据量：30天共约15万条申请，查询秒级返回。

## 12. 思考题

- 为什么要在模拟数据中制造异常？对后续开发监控系统有何帮助？
  → 可测试监控告警规则是否灵敏，验证 RCA 流程是否能定位到正确维度，确保系统在实际异常发生时能正确响应。
- 如果真实业务中某天申请量突然翻倍，作为数据工程师应如何排查？
  → 1. 确认数据源是否重复推送；2. 检查 ETL 是否重复计算；3. 与业务方确认是否有营销活动；4. 查看各渠道申请量分布，定位突增来源；5. 检查是否有爬虫或恶意攻击。
