# Day 8 实践报告：分区裁剪与列裁剪验证

## 1. 练习目标
- 理解 **分区裁剪（Partition Pruning）**：通过 WHERE 条件只扫描所需分区，避免全表扫描。
- 理解 **列裁剪（Column Pruning）**：只 SELECT 必要的列，减少 I/O 和内存开销。
- 使用 DuckDB 的 `EXPLAIN` 观察执行计划，验证优化效果。

## 2. 实验环境
- 数据路径：`data/raw/apply/` 按 `dt` 分区（3 个分区：2024-01-01, 2024-01-02, 2024-01-03）
- 视图：`v_apply`（基于分区 Parquet 文件创建，`hive_partitioning=1`）

## 4. 结论与性能收益

- **分区裁剪**：将扫描的文件数从 3 个减少到 1 个，理论上减少约 66% 的 I/O 和数据处理量。
- **列裁剪**：在第一个查询中读取了 7 列，第二个查询只读取 2 列（加上隐含的分区列），进一步减少了内存和网络开销。
- 两种优化叠加，可显著提升查询性能，尤其是在大数据量场景下。

## 5. 口径与边界说明

- **口径**：同一指标（例如 `apply_id`、`amount`）在 `SELECT *` 与 `SELECT 必要列` 下的结果完全一致，验证了列裁剪不影响数据准确性。实践中应记录扫描列的差异，以明确优化效果。
- **边界**：
  - 如果后续处理步骤（如下游ETL任务或应用接口）依赖未被 SELECT 的字段，则会导致字段缺失错误，影响数据链路的完整性。
  - 因此，必须在数据文档中明确列出 **“必要字段清单”**，确保上下游模块对该清单达成一致，避免因列裁剪引发生产故障。

## 6. 学习笔记 / 面试要点

- 在 Hive/Spark/DuckDB 中，分区裁剪要求表定义时使用分区列，且查询中尽量使用分区列过滤。
- 列裁剪通常由查询引擎自动完成（如 DuckDB 的 `read_parquet` 会推投影下推），但编写查询时应**只 SELECT 必要列**，既是良好习惯，也帮助优化器做更好决策。
- `EXPLAIN` 是验证执行计划是否最优的重要工具。
