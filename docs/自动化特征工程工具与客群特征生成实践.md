# 自动化特征工程工具与客群特征生成实践

## 一、自动化特征工程工具核心解析：以 Featuretools 为例

### 1.1 工具定位与核心价值

自动化特征工程工具（以 **Featuretools** 为代表）是面向数据科学与数据分析领域的开源工具，核心价值在于**替代人工完成繁琐的特征构建、特征衍生工作**，大幅降低特征工程的时间成本，同时提升特征的多样性与深度。

传统特征工程依赖人工经验，需手动处理数据关联、特征聚合、时间序列衍生等操作，不仅效率低下，还容易遗漏关键特征；而 Featuretools 基于**深度特征合成（Deep Feature Synthesis, DFS）** 算法，可自动从多表关联数据中挖掘多层级、高维度的特征，实现 “从数据到特征” 的自动化流转。

### 1.2 核心原理与关键概念

#### （1）深度特征合成（DFS）算法

DFS 是 Featuretools 的核心算法，其核心逻辑是：

- 以**实体（Entity）** 为数据单元（如用户表、订单表、申请记录表），以**关系（Relationship）** 关联实体间的逻辑（如 “用户 - 订单” 的一对多关系）；

- 从基础特征出发，通过

  聚合（Aggregation）、变换（Transform）两种核心操作，逐层构建深度特征：

  - 聚合操作：对多记录数据进行统计汇总（如求和、均值、最大值、计数、去重数等），适用于 “一对多” 关系（如统计每个用户的订单总数）；
  - 变换操作：基于单条记录的多字段进行计算衍生（如比值、差值、百分比、时间差等），适用于 “一对一” 或单表内特征衍生。

#### （2）核心概念详解

| 概念                       | 定义                                           | 业务示例                                                     |
| :------------------------- | :--------------------------------------------- | :----------------------------------------------------------- |
| 实体（Entity）             | 二维数据表的抽象，对应业务中的核心对象         | 用户实体（user 表）、申请实体（apply 表）、订单实体（order 表） |
| 关系（Relationship）       | 实体间的逻辑关联（一对一 / 一对多 / 多对多）   | 一个用户对应多次申请（user.id = apply.user_id，一对多）      |
| 特征基元（Primitive）      | 特征构建的基本操作单元，分为聚合基元、变换基元 | 聚合基元：Count（计数）、Mean（均值）；变换基元：TimeSince（时间差）、Ratio（比值） |
| 深度特征（Deep Feature）   | 经过多层基元操作合成的、具备业务语义的复杂特征 | 基于 “用户 - 申请” 关系，合成 “用户近 30 天申请平均通过率”（多层聚合 + 变换） |
| 特征矩阵（Feature Matrix） | 自动化生成的、可直接用于模型训练的特征数据集   | 以用户为行，以所有衍生特征为列的二维矩阵                     |

### 1.3 工具核心优势

1. **自动化程度高**：无需手动编写大量特征衍生代码，输入多表数据与关系后，自动生成数百至数千个特征；
2. **特征深度足**：支持多层级特征合成，可挖掘人工易忽略的隐性特征（如用户历史行为的间接关联特征）；
3. **可扩展性强**：支持自定义特征基元，适配不同业务场景的特殊需求（如风控场景下的 “风险评分”“逾期概率” 等专属特征）；
4. **兼容生态完善**：支持 Pandas DataFrame 数据格式，可与 Scikit-learn、XGBoost 等机器学习框架无缝对接。

## 二、风控场景下客群特征自动生成实践

### 2.1 客群特征的业务定义

风控场景中的**客群特征**，核心是围绕 “目标客群（如借款人、申请人）” 的历史行为、资产状况、履约记录等数据，挖掘能够反映客群风险水平的特征。这类特征是风控模型（如信用评分模型、反欺诈模型）的核心输入，直接决定模型的预测效果。

常见客群特征分类及业务含义：

| 特征类别   | 核心特征示例                                | 业务风险含义                                         |
| :--------- | :------------------------------------------ | :--------------------------------------------------- |
| 行为类特征 | 历史申请次数、近 7 天申请频次、申请渠道分布 | 申请行为越频繁，风险可能越高；多渠道申请存在欺诈嫌疑 |
| 履约类特征 | 历史逾期次数、平均逾期天数、还款成功率      | 履约记录越差，逾期风险越高                           |
| 资产类特征 | 名下资产总额、资产类型占比、月均收入        | 资产越充足，风险承受能力越强                         |
| 关联类特征 | 关联人申请次数、关联设备重复率              | 关联人 / 设备异常可能是欺诈信号                      |

### 2.2 基于 Featuretools 的客群特征生成流程

#### 步骤 1：数据准备与实体定义

首先梳理风控场景的核心业务数据，构建多表实体数据集，以 “用户申请风控场景” 为例，核心实体及数据字段如下：

1. **用户实体（user）**：核心主键为 user_id，字段包括：年龄、性别、职业、月收入、户籍所在地、注册时间等；
2. **申请实体（apply）**：核心主键为 apply_id，外键为 user_id，字段包括：申请时间、申请金额、申请渠道、贷款期限、审批结果（通过 / 拒绝）、放款金额等；
3. **履约实体（repay）**：核心主键为 repay_id，外键为 user_id，字段包括：还款时间、应还金额、实还金额、逾期状态（正常 / 逾期）等。

将上述数据转换为 Pandas DataFrame，作为 Featuretools 的输入数据。

#### 步骤 2：定义实体间关系

基于业务逻辑，明确实体间的关联关系，使用 `Relationship` 类定义：

```python
import featuretools as ft

# 1. 创建实体集（EntitySet）
es = ft.EntitySet(id="risk_customer_es")

# 2. 添加实体到实体集
# 用户实体
es = es.add_dataframe(
    dataframe=user_df,
    entity_name="user",
    index="user_id",
    time_index="register_time"  # 时间索引，用于时间序列特征生成
)

# 申请实体
es = es.add_dataframe(
    dataframe=apply_df,
    entity_name="apply",
    index="apply_id",
    time_index="apply_time"  # 申请时间，用于时间窗口特征生成
)

# 履约实体
es = es.add_dataframe(
    dataframe=repay_df,
    entity_name="repay",
    index="repay_id",
    time_index="repay_time"
)

# 3. 定义实体间关系
# 用户-申请：一对多关系（一个用户对应多次申请）
rel_user_apply = ft.Relationship(
    parent_entity=es["user"],
    child_entity=es["apply"],
    parent_column="user_id",
    child_column="user_id"
)

# 用户-履约：一对多关系（一个用户对应多笔履约记录）
rel_user_repay = ft.Relationship(
    parent_entity=es["user"],
    child_entity=es["repay"],
    parent_column="user_id",
    child_column="user_id"
)

# 添加关系到实体集
es = es.add_relationship(rel_user_apply)
es = es.add_relationship(rel_user_repay)
```

#### 步骤 3：配置特征生成参数与执行 DFS 算法

核心是指定**目标实体**（客群特征的核心对象，即 “user” 实体）、**特征基元**（根据业务场景选择合适的聚合 / 变换基元），以及**时间窗口参数**（避免数据泄露），然后执行 DFS 算法生成特征。

```python
# 1. 定义特征基元（按需选择，也可使用默认基元）
# 聚合基元：统计申请、履约相关的统计特征
agg_primitives = [
    ft.Count,  # 申请次数、履约次数
    ft.Mean,  # 申请金额均值、逾期金额均值
    ft.Max,  # 最大申请金额、最大逾期天数
    ft.NUnique,  # 申请渠道去重数
    ft.Sum  # 总申请金额、总逾期金额
]

# 变换基元：基于单表/单记录的特征衍生
trans_primitives = [
    ft.TimeSince,  # 距离上次申请的时间、距离上次逾期的时间
    ft.Day,  # 申请日期对应的星期几
    ft.IsWeekend  # 是否为周末申请
]

# 2. 执行深度特征合成（生成客群特征）
# target_entity：目标实体为用户，生成以用户为单位的客群特征
# cutoff_time：时间截断点（风控场景需严格遵守时间逻辑，避免数据泄露）
feature_matrix, feature_defs = ft.dfs(
    entityset=es,
    target_entity="user",
    agg_primitives=agg_primitives,
    trans_primitives=trans_primitives,
    cutoff_time=cutoff_time_df,  # 关键：指定每个用户的特征生成时间截断点
    max_depth=3,  # 特征合成的最大深度，避免特征过于复杂
    verbose=True
)

# 3. 查看生成的客群特征
print("生成的客群特征列表：")
for feat in feature_defs:
    print(feat)

# 4. 查看特征矩阵（可直接用于模型训练）
print("\n客群特征矩阵（前5行、前10列）：")
print(feature_matrix.iloc[:5, :10])
```

#### 步骤 4：特征筛选与业务校验

Featuretools 自动生成的特征数量较多（可能包含数千个），且部分特征无业务意义或存在共线性，需进行人工筛选与业务校验，核心步骤如下：

1. **剔除无业务意义特征**：如全为 0 / 全为 1 的特征、方差极低的特征（方差阈值法）；
2. 避免数据泄露：
3. 这是风控场景的核心禁忌，需重点校验：
   - 特征是否使用了 “未来数据”（如用申请结果的标签生成特征，再用于预测申请结果）；
   - 特征是否跨越了业务时间窗口（如用用户逾期 3 个月后的记录生成近 1 个月的申请特征）；
   - 解决方案：通过 `cutoff_time` 参数严格限定特征生成的时间范围，确保 “特征仅使用历史数据”；
4. **共线性处理**：计算特征间的相关系数，剔除高度相关的特征（如相关系数 > 0.9），降低模型复杂度与过拟合风险；
5. **业务语义校验**：结合风控业务经验，验证特征的合理性（如 “用户近 30 天申请通过率” 为负数时，需排查数据问题）。

## 三、自动化生成客群特征的关键注意事项

### 3.1 核心风险：数据泄露（风控场景重中之重）

数据泄露是自动化特征工程在风控场景中最易出现的问题，指**特征生成时使用了未来时间点的数据或业务标签数据**，导致模型在训练集上表现优异，但上线后预测效果极差。

#### 避免数据泄露的核心措施：

1. **严格遵守时间顺序**：所有客群特征必须基于 “目标时间点之前的历史数据” 生成，例如：预测用户 2024 年 3 月的申请逾期风险，只能使用 2024 年 3 月之前的申请、履约数据；
2. **使用时间截断（Cutoff Time）**：Featuretools 支持通过 `cutoff_time` 参数为每个用户指定特征生成的时间截断点，确保仅使用该时间点之前的数据生成特征；
3. **禁止使用目标变量生成特征**：严禁将 “是否逾期”“是否通过” 等目标标签作为特征的一部分，否则会导致模型直接 “记住” 标签，失去泛化能力；
4. **特征上线前二次校验**：上线前需抽样检查特征的时间逻辑，确保无跨时间窗口的特征。

### 3.2 特征质量与业务结合

自动化生成的特征虽多，但并非全部可用，需坚持 “**业务优先，自动化辅助**” 的原则：

1. **保留核心业务特征**：对于风控领域的关键特征（如用户月收入、历史逾期次数），即使自动化工具未生成，也需手动添加；
2. **自定义特征基元**：针对风控特殊场景，开发自定义基元（如 “逾期金额 / 申请金额比值”“关联设备风险评分”），提升特征的针对性；
3. **特征解释性**：风控模型要求具备可解释性，需优先保留业务语义清晰、可解释性强的特征，避免过度复杂的 “黑盒特征”。

### 3.3 工具适配性与成本控制

1. **数据量适配**：Featuretools 适合中小规模的多表数据，若数据量达到亿级，需进行数据抽样或分布式计算优化，避免工具运行效率过低；
2. **轻量化使用**：无需每次生成全部特征，可根据业务迭代需求（如新增申请渠道、新增履约字段），针对性调整基元与实体关系；
3. **团队能力匹配**：需确保团队掌握 Featuretools 的核心原理与使用方法，同时具备风控业务经验，才能实现 “自动化生成 + 人工校验” 的高效闭环。

## 四、总结

自动化特征工程工具（如 Featuretools）是风控客群特征生成的高效工具，核心价值在于**自动化挖掘深度特征、提升特征工程效率**。基于该工具，可快速从多表关联数据中生成行为类、履约类、关联类等客群特征，但需严格遵守风控业务规则，避免数据泄露，同时结合业务经验进行特征筛选与校验，最终实现 “自动化工具 + 人工智慧” 的结合，提升风控客群特征的质量与模型的预测效果。

未来，随着风控场景数据维度的丰富（如设备数据、行为日志数据），自动化特征工程将进一步结合时序特征、图特征等技术，为风控客群特征生成提供更全面的解决方案。
