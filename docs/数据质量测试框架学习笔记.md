# 数据质量测试框架学习笔记
## 一、数据质量测试框架核心认知
### 1. 核心定义
数据质量测试框架是将数据质量规则（如完整性、准确性、一致性、唯一性）转化为可执行、可复用、可监控的自动化测试的工具集，解决人工校验效率低、规则不统一、问题发现滞后的痛点，是数据仓库/数据平台质量保障的核心组件。

### 2. 主流框架（Great Expectations、Soda）核心能力对比
| 能力维度        | Great Expectations（GX）                                     | Soda                                                         |
| --------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 规则定义方式    | 自定义 `Expectation`（Python API/JSON 配置），支持内置 50+ 通用规则 | 基于 SQL/YAML 定义检查规则，SQL 驱动更贴合数仓工程师使用习惯 |
| 核心优势        | 自动生成数据文档、支持字段级细粒度校验、数据探查能力强       | 轻量化、CI/CD 集成友好、支持无代码配置、多数据源适配（含 DuckDB） |
| 数据文档/可视化 | 自动生成交互式数据质量报告（HTML/PDF），包含校验结果和数据概览 | 生成简洁的校验报告，支持 CLI/UI 查看结果                     |
| 数据源适配      | 支持主流数据库（MySQL/PostgreSQL/DuckDB）、数据湖（S3/HDFS） | 全面适配关系型数据库、数仓工具，原生支持 DuckDB/Trino 等轻量化引擎 |
| 集成能力        | 支持 Airflow/Spark 集成，可嵌入数据流水线                    | 深度集成 CI/CD（GitLab/GitHub Actions），支持流水线卡点执行  |
| 学习成本        | 中等（需了解 Python/配置文件）                               | 低（SQL/YAML 为主，无编程基础也可上手）                      |

### 3. 数据质量规则分类（可落地的核心规则）
| 规则类型       | 示例场景                             | GX 对应 Expectation                   | Soda 对应 SQL 规则示例                                       |
| -------------- | ------------------------------------ | ------------------------------------- | ------------------------------------------------------------ |
| 完整性         | 核心字段（用户ID）非空               | `expect_column_values_to_not_be_null` | `SELECT COUNT(*) FROM table WHERE user_id IS NULL = 0`       |
| 唯一性         | 订单号列无重复值                     | `expect_column_values_to_be_unique`   | `SELECT COUNT(*) = COUNT(DISTINCT order_id) FROM table`      |
| 范围校验       | 金额列值 ≥ 0 且 ≤ 1000000            | `expect_column_values_to_be_between`  | `SELECT COUNT(*) FROM table WHERE amount < 0 OR amount > 1000000 = 0` |
| 枚举值校验     | 状态列仅包含「待支付/已支付/已取消」 | `expect_column_values_to_be_in_set`   | `SELECT COUNT(*) FROM table WHERE status NOT IN ('待支付','已支付','已取消') = 0` |
| 格式校验       | 手机号符合 11 位数字格式             | `expect_column_values_to_match_regex` | `SELECT COUNT(*) FROM table WHERE phone NOT REGEXP '^1[3-9]\\d{9}$' = 0` |
| 关联性（对账） | 订单表金额总和 = 支付表金额总和      | 自定义 Expectation（SQL 实现）        | `SELECT (SELECT SUM(amount) FROM order) = (SELECT SUM(amount) FROM payment)` |

## 二、实战：将对账规则转化为 Great Expectations 可执行测试
### 1. 环境准备
#### 前置依赖安装
```bash
# 安装 Great Expectations 核心库 + DuckDB 支持（适配本项目数据源）
pip install great-expectations duckdb great-expectations-plugin-duckdb
```

#### 初始化 GX 项目
```bash
# 创建并进入项目目录
mkdir gx_data_quality && cd gx_data_quality
# 初始化 GX 项目（生成配置文件和目录结构）
great_expectations init
```
执行后会生成如下目录结构：
```
gx_data_quality/
├── great_expectations/          # GX 核心配置目录
│   ├── expectations/            # 存储质量规则（Expectation）
│   ├── checkpoints/             # 测试执行配置
│   └── great_expectations.yml   # 全局配置
└── data/                        # 存放待测试的 DuckDB 文件
```

### 2. 核心步骤：定义对账规则的 Expectation
以「订单表总金额 = 支付表总金额」的对账规则为例，实现可执行测试：

#### 步骤1：配置数据源（对接 DuckDB）
编辑 `great_expectations/great_expectations.yml`，添加 DuckDB 数据源配置：
```yaml
datasources:
  duckdb_datasource:
    class_name: Datasource
    execution_engine:
      class_name: DuckDBExecutionEngine
      connection_string: "data/dev.duckdb"  # 替换为你的 DuckDB 文件路径
    data_connectors:
      default_inferred_data_connector_name:
        class_name: InferredAssetFilesystemDataConnector
        base_directory: ./data
        default_regex:
          pattern: (.*)\.duckdb
          group_names:
            - data_asset_name
```

#### 步骤2：创建 Expectation（定义对账规则）
创建文件 `great_expectations/expectations/reconciliation_expectations.py`，编写自定义对账规则：
```python
from great_expectations.core.expectation_configuration import ExpectationConfiguration
from great_expectations.expectations.expectation import QueryExpectation

class ExpectReconciliationOrderPaymentAmount(QueryExpectation):
    """
    自定义对账规则：订单表总金额 = 支付表总金额
    """
    # 规则唯一标识
    expectation_type = "expect_reconciliation_order_payment_amount"
    # 规则描述
    meta = {
        "description": "校验订单表总金额与支付表总金额相等",
        "tags": ["对账", "金额校验", "自定义规则"],
        "authors": ["数据质量工程师"],
    }

    # 核心：执行对账的 SQL 查询
    query = """
    SELECT 
        CASE 
            WHEN (SELECT COALESCE(SUM(amount), 0) FROM order_table) = (SELECT COALESCE(SUM(amount), 0) FROM payment_table) 
            THEN 1 
            ELSE 0 
        END AS reconciliation_result
    """

    # 校验逻辑：查询结果为 1 则通过
    success_keys = ("value",)
    default_kwarg_values = {"value": 1}

    def validate_configuration(self, configuration):
        """校验配置合法性"""
        super().validate_configuration(configuration)
        return True

# 注册自定义 Expectation
if __name__ == "__main__":
    ExpectReconciliationOrderPaymentAmount().print_diagnostic_checklist()
```

#### 步骤3：创建 Checkpoint（执行测试）
创建文件 `great_expectations/checkpoints/reconciliation_checkpoint.yml`：
```yaml
name: reconciliation_checkpoint
config_version: 1.0
class_name: SimpleCheckpoint
run_name_template: "对账规则测试 - {run_time}"
validations:
  - batch_request:
      datasource_name: duckdb_datasource
      data_connector_name: default_inferred_data_connector_name
      data_asset_name: dev  # 对应 DuckDB 文件名（dev.duckdb）
    expectation_suite_name: reconciliation_suite
action_list:
  - name: store_validation_result
    action:
      class_name: StoreValidationResultAction
  - name: store_evaluation_params
    action:
      class_name: StoreEvaluationParametersAction
  - name: update_data_docs
    action:
      class_name: UpdateDataDocsAction
```

#### 步骤4：执行测试并生成报告
```bash
# 加载自定义 Expectation 并执行测试
great_expectations checkpoint run reconciliation_checkpoint
```

### 3. 测试结果查看
1. **命令行输出**：直接显示测试通过/失败，以及失败时的金额差异；
2. **数据文档（可视化报告）**：执行后自动生成 HTML 报告，路径为 `great_expectations/uncommitted/data_docs/local_site/`，打开 `index.html` 可查看：
   - 对账规则的详细定义；
   - 测试执行结果（通过/失败）；
   - 失败时的具体数据差异（如订单表总金额 10000，支付表 9990）。

### 4. 轻量化实践：Soda 实现对账规则测试（SQL 驱动）
若更倾向 SQL 方式，可使用 Soda 快速实现，步骤如下：

#### 步骤1：安装 Soda + 配置数据源
```bash
# 安装 Soda Core
pip install soda-core-duckdb
```
创建 `soda_config.yml`：
```yaml
data_source duckdb_data:
  type: duckdb
  connection:
    database: data/dev.duckdb  # 你的 DuckDB 文件路径
```

#### 步骤2：定义对账规则（soda_checks.yml）
```yaml
checks for duckdb_data:
  - check: 订单支付金额对账
    description: 校验订单表总金额等于支付表总金额
    sql: |
      SELECT 
          (SELECT COALESCE(SUM(amount), 0) FROM order_table) AS order_total,
          (SELECT COALESCE(SUM(amount), 0) FROM payment_table) AS payment_total
      WHERE order_total != payment_total
    fail:
      when returned row count > 0: "对账失败：订单总金额 {order_total} ≠ 支付总金额 {payment_total}"
```

#### 步骤3：执行测试
```bash
soda scan -d duckdb_data -c soda_config.yml soda_checks.yml
```
执行后会输出清晰的测试结果，失败时直接显示金额差异，可集成到 CI/CD 流水线（如 GitHub Actions）实现自动化监控。

## 三、落地建议与扩展
### 1. 规则落地优先级
1. 核心字段校验（非空、唯一）→ 基础且高价值；
2. 业务规则校验（范围、枚举）→ 贴合业务场景；
3. 跨表对账规则 → 解决核心业务对账痛点；
4. 数据分布校验（如均值、分位数）→ 监控数据异常波动。

### 2. 集成到数据流水线
- **Great Expectations**：嵌入 Airflow DAG，在数据入库后执行质量测试，失败则告警/回滚；
- **Soda**：集成到 GitLab CI/CD，每次 SQL 脚本提交后自动执行质量检查，卡点合并。

### 3. 本项目适配建议
1. 将现有手动对账规则（如金额、订单数）转化为上述 GX/Soda 规则；
2. 针对 DuckDB 数据源，优先使用 Soda（轻量化、SQL 驱动）或 GX 的 DuckDB 插件；
3. 定期执行测试并生成报告，替换人工对账，提升效率和准确性。

## 总结
### 核心要点
1. 数据质量测试框架的核心价值：将「人工校验规则」转化为「可执行的自动化测试」，实现质量问题早发现、可追溯；
2. Great Expectations 适合需要数据文档、细粒度校验的场景，Soda 适合轻量化、SQL 驱动、CI/CD 集成的场景；
3. 对账规则落地：通过自定义 SQL 实现跨表校验，是企业级数据质量保障的核心场景之一。

### 实践路径
1. 从基础规则（非空、唯一）入手，熟悉框架使用；
2. 逐步迁移核心对账规则到自动化测试；
3. 集成到数据流水线，实现全流程质量监控。
