# 数据版本控制工具学习笔记

## 一、核心数据版本控制工具基本概念

### 1. DVC（Data Version Control）

- **核心定位**：开源的分布式数据版本控制系统，专为机器学习 / 数据工程场景设计，被称为「数据领域的 Git」，解决 Git 无法高效管理大文件（数据集、模型文件、ETL 产出数据）的问题。

- 核心原理：

  - 不直接存储大文件内容，而是将文件哈希值（MD5/SHA256）存入 Git 仓库，实际数据文件存储在本地 / 远程存储（如 S3、MinIO、本地磁盘）；
  - 支持数据版本分支、回滚、合并，与 Git 无缝集成（代码用 Git 管理，数据用 DVC 管理）。

- 核心功能：

  - 数据集 / 模型版本管理：标记不同阶段的数据集（如「20260311_ods_raw」「20260312_ods_increment」），支持一键回滚到历史版本；
  - 数据依赖追踪：定义数据管道（如「原始数据→ODS 层→DWD 层」），追踪每一步数据变换的来源和输出；
  - 高效传输：支持增量同步、数据缓存，避免重复传输大文件。

- 适配场景：

  - 风控数仓中 ODS/DWD 层数据版本标记（如每日 ETL 产出的信贷申请数据）；
  - 机器学习模型训练数据版本管理（如不同批次训练数据的对比）。

  

### 2. LakeFS（补充了解）

- **核心定位**：面向数据湖的版本控制工具，聚焦「数据湖级」的版本管理，适配 HDFS、S3、OSS 等分布式存储。

- 核心特点：

  - 以「分支」「提交」「合并」为核心，支持数据湖的原子性操作（如 ETL 任务失败时回滚整个数据湖分区）；
  - 内置数据血缘追踪，可查看 ODS 层数据到 DWD 层的版本流转；
  - 支持数据隔离（如开发分支、生产分支），避免 ETL 测试数据污染生产数据。

- 适配场景：

  - 大规模数仓（TB/PB 级）的版本管理；
  - 湖仓一体架构下的 ETL 流程版本控制。

  

## 二、数据版本控制在 ETL 流程中的落地思路

### 1. 核心应用场景

针对风控数仓的 ODS/DWD 层数据，通过版本控制解决以下问题：

- ETL 任务异常时快速回滚到上一版有效数据；
- 对比不同日期 ETL 产出数据的差异（如字段缺失、数据量波动）；
- 审计合规要求：记录每一次 ETL 的数据版本，满足金融行业数据溯源要求。

### 2. 轻量化落地方案（适配本项目）

考虑到项目初期复杂度，无需直接部署 DVC/LakeFS，可先通过「审计日志 + 数据分区标记」实现轻量级版本控制，后续可平滑迁移到 DVC：

#### 步骤 1：ETL 审计日志设计

创建 `etl_version_log` 表，记录每次 ETL 的核心信息（版本标记、数据范围、执行结果）：

```sql
-- 审计日志表（MySQL/数仓表）
CREATE TABLE etl_version_log (
    version_id VARCHAR(32) PRIMARY KEY COMMENT '版本ID（如20260311_ods_credit）',
    layer VARCHAR(16) COMMENT '数据层（ODS/DWD/DWS）',
    table_name VARCHAR(64) COMMENT '表名',
    etl_start_time DATETIME COMMENT 'ETL开始时间',
    etl_end_time DATETIME COMMENT 'ETL结束时间',
    data_start_date DATE COMMENT '数据起始日期',
    data_end_date DATE COMMENT '数据结束日期',
    record_count INT COMMENT '本次ETL写入记录数',
    status VARCHAR(8) COMMENT '执行状态（success/fail）',
    operator VARCHAR(32) COMMENT '执行人员/系统',
    remark VARCHAR(256) COMMENT '备注（如增量/全量、变更说明）'
);
```

#### 步骤 2：ETL 脚本中嵌入版本标记

在 `etl_load_ods.py` 中添加版本生成和日志写入逻辑：

```python
import hashlib
import datetime
import pandas as pd
from sqlalchemy import create_engine

# 1. 生成唯一版本ID（日期+表名+哈希）
def generate_version_id(layer, table_name):
    date_str = datetime.datetime.now().strftime('%Y%m%d')
    base_str = f"{date_str}_{layer}_{table_name}"
    hash_str = hashlib.md5(base_str.encode()).hexdigest()[:8]
    return f"{base_str}_{hash_str}"

# 2. 执行ETL并记录日志
def etl_load_ods():
    # 基础配置
    layer = "ODS"
    table_name = "ods_credit_apply"
    version_id = generate_version_id(layer, table_name)

    # 初始化日志参数
    log_data = {
        "version_id": version_id,
        "layer": layer,
        "table_name": table_name,
        "etl_start_time": datetime.datetime.now(),
        "data_start_date": data_date,
        "data_end_date": data_date,
        "record_count": 0,
        "status": "fail",
        "operator": "airflow_scheduler",
        "remark": "每日增量加载ODS层信贷申请数据"
    }
    
    try:

        # 更新日志参数
        log_data["etl_end_time"] = datetime.datetime.now()
        log_data["record_count"] = len(clean_data)
        log_data["status"] = "success"
    except Exception as e:
        log_data["remark"] += f"；执行失败：{str(e)[:100]}"
        raise e
    finally:
        # 写入审计日志

    return version_id
```

#### 步骤 3：历史版本对比与回溯

通过审计日志和数据分区实现轻量级版本管理：

- 版本查询：查询 `etl_version_log` 表获取指定日期的版本 ID，关联数据分区（如 `ods_credit_apply_20260311`）；

- 版本对比：通过 SQL 对比不同版本的数据量、字段值分布：

  ```sql
  -- 对比20260310和20260311的ODS层数据量差异
  SELECT 
      a.version_id, a.record_count, b.version_id, b.record_count,
      ABS(a.record_count - b.record_count) AS diff_count
  FROM etl_version_log a
  JOIN etl_version_log b 
    ON a.table_name = b.table_name 
    AND a.layer = b.layer
  WHERE a.version_id LIKE '20260310_ods_credit%'
    AND b.version_id LIKE '20260311_ods_credit%';
  ```

- 版本回溯：若 ETL 异常，删除当日分区数据，重新执行历史版本的 ETL 脚本。

### 3. 进阶落地（DVC 集成方案）

当项目规模扩大后，可接入 DVC 实现标准化版本控制：

#### 步骤 1：DVC 基础配置

```bash
# 1. 初始化DVC（与Git仓库集成）
git init
dvc init

# 2. 配置远程数据存储（如本地磁盘）
dvc remote add -d myremote /data/dvc_storage

# 3. 跟踪ODS层数据文件（如Parquet格式）
dvc add data/ods/credit_apply

# 4. 提交版本（Git存元数据，DVC存实际数据）
git add data/ods/credit_apply.dvc .dvc/config
git commit -m "Add ODS credit apply data 20260311"
dvc push
```

#### 步骤 2：版本回溯与对比

```bash
# 回滚到上一版本数据
git checkout HEAD~1 data/ods/credit_apply.dvc
dvc checkout

# 对比两个版本的数据差异
dvc diff <old_version> <new_version> --data
```

## 四、工具选型建议（成都本地场景）

| 维度         | DVC                       | LakeFS                           | 适配场景                                    |
| :----------- | :------------------------ | :------------------------------- | :------------------------------------------ |
| 适用规模     | 中小规模（GB/TB 级）      | 大规模（TB/PB 级）               | 风控数仓初期用 DVC，数仓扩容后迁移到 LakeFS |
| 学习成本     | 低（与 Git 兼容，易上手） | 中（需了解数据湖架构）           | 转行阶段优先掌握 DVC 基础用法               |
| 集成难度     | 低（可嵌入现有 ETL 脚本） | 高（需部署独立服务）             | 项目初期优先轻量级审计日志，后期接入 DVC    |
| 成都公司适配 | 中（中小公司广泛使用）    | 高（头部金融科技公司如兴业数金） | 面试重点提及 DVC，了解 LakeFS 概念即可      |

### 总结

1. 数据版本控制的核心价值是**数据溯源、版本回溯、差异对比**，适配风控数仓的审计和故障恢复需求；
2. 项目初期可通过「ETL 审计日志 + 数据分区」实现轻量级版本控制，降低落地成本；
3. DVC 是数据工程师必备的版本控制工具，掌握其核心用法（初始化、版本标记、回溯）可提升简历竞争力，适配成都金融 / 数仓类岗位需求。
