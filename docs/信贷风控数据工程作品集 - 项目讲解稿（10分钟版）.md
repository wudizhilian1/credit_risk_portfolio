**自我介绍**：

**业务痛点**：

**项目目标**：
- 建立标准化、分层的数据仓库（ODS → DWD → DWS → ADS）
- 实现核心风控指标自动化计算与可视化

## 2. 数据架构与技术栈（2分钟）

**数据分层设计**：
- **ODS 层**：原始数据接入，保留所有明细，按加载日分区，容忍重复和脏数据。
- **DWD 层**：清洗去重，按业务主键取最新状态，形成干净的事实明细。
- **DWS 层**：按常用维度预聚合，生成渠道日报、策略日报、拒绝原因 TopN、客群分层等汇总表。
- **ADS 层**（规划中）：面向最终报表的应用层，如风控看板、渠道质量榜。

**核心表设计**：
- 事实表：`ods_apply`、`ods_decision`、`dwd_apply_latest`、`dwd_decision_latest`
- 维表：`dim_channel`、`dim_customer`、`dim_strategy`、`dim_reject_reason`
- 汇总表：`dws_channel_daily`、`dws_strategy_daily`、`dws_reject_topn_daily`、`dws_segment_daily`、`dws_segment_strategy_daily`

**技术栈**：
- 数据存储与计算：DuckDB（列式存储，支持 SQL 窗口函数，本地化运行）
- ETL 脚本：Python 封装 SQL 执行，支持参数化日期和幂等操作
- 调度：目前为手动/脚本批量运行，后续可集成 Airflow 或 cron
- 监控：通过 SQL 构建 DQ 规则，结果写入监控表，可对接邮件/钉钉告警

## 3. 核心指标与分层评估（2分钟）

**指标口径**（以 `pass_rate` 为例）：
- 定义：`COUNT(DISTINCT CASE WHEN decision = 'PASS' THEN apply_id END) / COUNT(DISTINCT apply_id) * 100`
- 数据来源：`dwd_apply_latest` 左连 `dwd_decision_latest`，取最新决策
- 边界处理：分母为 0 时返回 NULL，避免除零错误

**多维度分析**：
- 渠道日报：监控各渠道申请量、通过率，发现渠道质量差异。
- 策略日报：对比不同策略版本的通过率，评估策略效果。
- 拒绝原因 TopN：定位主要拒绝原因，为策略优化提供方向。
- 客群分层：按新老客、额度区间细分，观察不同客群表现。
- 交叉分析：将策略与客群结合，例如发现 v1.0 策略在新客中通过率显著偏低，可针对性调整。

**成果示例**：
- 通过 `dws_channel_daily` 发现 APP 渠道通过率长期低于 WEB，需要排查渠道风险或策略误杀。
- 通过 `dws_strategy_daily` 对比 v1.0 与 v2.0，v2.0 通过率提升但拒绝率同步下降，说明策略更宽松但未增加风险（需要结合坏账率验证）。

## 4. 异常场景与监控体系（2分钟）

**模拟的异常数据**：
- 申请量突增（2024-01-15，营销活动）
- 渠道缺失（2024-01-18，API 接口故障）
- 通过率骤降（2024-01-20，策略误杀）
- 金额异常（2024-01-25，源系统 bug 产生负数）

**数据质量监控**：
- 行数波动：每日对比 DWS 表行数，超过 ±20% 触发 ERROR 告警，±10% 触发 WARN。
- 空值检测：`strategy_name` 等关键字段空值率 >0 即告警。
- 负值检测：`apply_cnt` 等数值字段出现负值直接报错。
- PSI 稳定性监控：计算拒绝原因分布与 7 天前的 PSI，大于 0.25 触发漂移告警。

**根因分析（RCA）**：
- 通过贡献拆解，定位到 WEB 渠道是 2024-01-20 通过率下降的主要贡献者。
- 进一步钻取 WEB 渠道的拒绝原因，发现 `RISK_SCORE` 拒绝占比上升，提示风险评分策略可能过严。
- 抽取样本申请 ID 供业务复查，确认策略误杀。

**成果**：
- 监控脚本每日自动执行，将告警写入 `dq_dws_monitor` 表，支持后续集成通知。
- PSI 监控帮助提前发现模型/策略漂移，避免风险累积。

## 6. 总结与 QA（1分钟）

**项目亮点**：
- **端到端**：从原始数据到监控告警，完整覆盖数仓建设生命周期。
- **可复现**：本地 DuckDB 即可运行，无需大数据集群，适合作品集展示。
- **业务价值**：指标口径统一、监控主动、归因清晰，直接支持风控策略调优。

**问题准备**：
- Q：为什么选择 DuckDB 而不是 Spark？  
  A：项目目标是快速构建可演示的作品集，DuckDB 轻量、易用，且支持标准 SQL 和分区读取，完全满足当前数据量级。若数据量增长，可平滑迁移到 Spark。
- Q：如何处理迟到数据？  
  A：ODS 层保留加载日分区，DWD 层按事件日重新组织，每日调度时检测迟到并触发历史分区重算，保证业务口径正确。
- Q：如何保证 SQL 幂等性？  
  A：所有 ETL 脚本均采用“先删后插”策略，如 `DELETE FROM ... WHERE dt = ...` 再 `INSERT`，多次执行结果一致。
